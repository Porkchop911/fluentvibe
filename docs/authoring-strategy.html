fluentvibe · strategy proposal

Authoring quality strategy

Date 23 Sep 2026 Status proposal, no code changes Fixed Tecan Fluent .xscr output · local LLMs Companion docs/architecture-roadmap-2026-09.md

1 · Summary

Today the local model is asked to do four jobs at once: understand a 40-page lab document, decide what belongs on the deck, write 500–600 lines of low-level head operations, and repair them against a simulator. It fails in two ways. Either it never converges (27B: 0 of 10 correct bead cleanups), or it converges on something that passes every check and is still wrong on the bench (Flash Next, 23 Sep).

Thesis. Move correctness out of the model and into deterministic layers. The model's job shrinks to what only a language model can do: read the document, state what the protocol is, and choose parameters. Verified building blocks produce correct liquid handling. Deterministic checks guard what the model says. You confirm its understanding at one cheap checkpoint.

MOVE 1

Verified building blocks + semantic checks

Fixes tip reuse, faked steps, wrong derived volumes and cleanup chemistry. Output shrinks about 5×.

MOVE 2

Extract → checkpoint → map → compose

Fixes understanding errors (pooling order, off-deck steps) that no code repair can fix.

MOVE 3

Harness efficiency

Forced first tool, lookup tool, patch-style repair, reasoning budget. About 49 min → an estimated 10–15 min.

The architecture roadmap covers the platform: state isolation, a shared build contract and model profiles. This document covers generation quality. It relies on the roadmap's P1: simulation must stop mutating authored labware before repeated scoring can be trusted.

What the evidence says

  1. Model capability isn't the only bottleneck. A stronger model reached a passing state that is still wrong. Better models turn "doesn't converge" into "converges on the wrong thing", and that looks done.
  2. The checks are the ceiling. Everything the model got wrong was something no gate measured. Each new deterministic check raises the floor for every model at once.
  3. Staging by protocol stage failed; staging by kind of reasoning is untried. The June staging still asked for low-level code in each stage.
  4. Output volume drives both latency and errors. 600 lines of head operations is 600 lines to get wrong and about 8k tokens per resubmission.

3 · Target pipeline

modelAExtract

Document + family skill → Bench Spec (YAML). Schema-constrained; every number must appear in the source.

youBCheckpoint

Spec shown as an editable table with source quotes. Approve, edit or re-extract. Cached for reuse.

codeCMap

Roles → labware and positions from the profile; liquid classes from the catalog map. The model only fills gaps.

modelDCompose

Spec + deck plan → a short Python file, mostly building-block calls.

codeECheck

Simulation + semantic checks against the spec: contamination, order, off-deck honesty, liquid classes.

modelFRepair

Patches one block call from diagnostics; never resubmits the whole file. Loops to E, then compiles to .xscr.

The 40–50k-token document is used only in stage A. Stages C–F see the spec, about 2–4k tokens.

4 · Workstreams

Size: S ≈ one focused session, M ≈ a few sessions, L ≈ a week or more.

W1 — Verified building-block library

Mnew folder: needs approval

Goal: the model never writes a bead cleanup, a pool or a column loop by hand again.

Promote workspace_modules.spri_cleanup into a standard library, fluentvibe.blocks, that every profile gets. Each block:

  • takes roles, not positions (sample_plate, magnet, waste) plus scientific parameters;
  • derives dependent volumes itself and exposes them as declared variables in the .xscr;
  • takes a tip policy (fresh_per_column default for anything that touches samples);
  • emits its steps inside a named wt.group carrying an origin ID, so diagnostics point back to the call;
  • has a docstring written for the model: preconditions, what it derives, one example call.

Changes: new fluentvibe/blocks/; move spri_cleanup there with a re-export; generate the blocks context for skills from the docstrings; family skills say "call spri_cleanup" instead of describing the steps.

Acceptance: unit tests per block (simulation, derived volumes, tip policy). A hand-written ONT protocol using blocks is under 120 lines, passes W3 and compiles. A re-run of the Flash case with blocks shows none of D1–D4 or D6.

Risk: blocks can hide head constraints. Keep raw operations first-class, and make blocks fail loud rather than silently adapt.

W2 — Bench Spec extraction and checkpoint

M–L

Goal: separate "what is the protocol" from "how to run it on this deck", and let you fix the first cheaply.

spec_version: 1
title: ONT SQK-RBK114 amplicon barcoding
samples: {count: 96, container: plate96, volume_ul: 9, analyte: "amplicon DNA"}
reagents:
  - {id: AXP, name: "AMPure XP beads", role: bead_carrier}
  - {id: EtOH80, name: "80% ethanol", role: wash, liquid_type: ethanol}
  - {id: RB, name: "Rapid Barcodes", role: per_sample, layout: plate96}
steps:
  - {id: s1, op: add, reagent: RB, volume_ul: 1, to: samples, location: deck}
  - {id: s2, op: incubate, temp_c: [30, 80], minutes: [2, 2], location: off_deck, device: thermal_cycler}
  - {id: s3, op: pool, from: samples, volume_ul: 10, to: {container: tube, name: pool}, location: deck}
  - {id: s4, op: bead_cleanup, target: pool, bead: AXP, ratio: 1.0, washes: 2, wash: EtOH80, elute_ul: 15}
  - {id: s5, op: manual, text: "Prime and load flow cell", location: manual}
source_refs: {s3: "p.14 'Pool all barcoded samples…'"}
  • One schema-constrained call. llama.cpp supports JSON-schema response formats and GBNF grammars, so malformed specs are impossible.
  • Input: document + relevant family skill(s) + schema. No deck, API or Python context.
  • Number check: every numeric value must appear in the source (units normalized); any that don't are flagged.
  • Location defaults come from verbs and devices ("thermal cycler", "Hula mixer", "centrifuge" → off_deck), and you can override them.
  • Checkpoint UI: a new panel in the authoring tab (not the setup/deck map) with an editable table and Approve / Edit / Re-extract. Approved specs are saved as bench_spec.yaml and reused.

Acceptance: for the ONT PDF, the spec has pooling before the second cleanup, marks thermal and flow-cell steps as off-deck or manual, and has no unflagged numbers missing from the source. Extraction ≤ 5 min on Flash Next.

Risk: the schema grows into a second DSL. Limit ops to families with blocks, plus manual and custom (which force a user prompt).

W3 — Deterministic semantic checks

Mdepends on roadmap P1

Goal: a protocol that simulates but is wrong on the bench fails, whichever model wrote it.

CheckMechanismCatches
Cross-contaminationTag each tip with the sample identities it has contacted (from the simulator's per-well layers); entering a well with a different sample set → violation, unless the tip is reagent-clean and dispensing from aboveD2
Spec conformanceMap operations back to spec steps via block origin IDs; every deck step has operations; order matches; pool reduces N→1D1
Off-deck honestyoff_deck/manual steps must lower to user_prompt (+ moves), never wait or a comment aloneD3
Liquid-class suitabilityReagent liquid_type → acceptable class patterns from the install catalog; volatile/viscous mismatch → errorD4
Derivation resolutionResolve values through Python constants and arithmetic before checking; a missing derivation fails instead of n/a when the stage existsD5 (rubric)
ConservationAnalyte proxy at the final destination ≈ 1 − expected losseslost or duplicated eluate

Rubric fixes (do first): derived_* resolves values through Python constants and fails instead of n/a when the stage exists without a derivation. Already in place since 7ebd18a: comment-only stages don't count as covered, and eluate_recovered requires a magnet round trip. Coverage still passed the Flash run because stage detection is keyword-based: the group name "…Clean-up and Pooling" satisfied the pooling stage. Only the semantic pooling check fixes that.

Acceptance: attempt 4 fails with D1–D4 named, and the rubric reports D5's derivations as pass, each with a line number. Hand-written examples/ stay green.

W6 — Evaluation

M
  • ~20 cases in three tiers. T1: simple transfers, stamping, reagent distribution. T2: single-family (cleanup, normalization, dilution). T3: multi-stage documents (ONT, ELISA, PCR setup). Each case has a reviewed spec and a gold protocol.
  • Metrics: spec accuracy, first-pass and final W3 pass rate, turns, output tokens, wall time, and incorrectly accepted (passed all gates, failed review). The last is the headline metric.
  • Runner: extend scripts/eval_authoring.py to run stages independently (e.g. compose-only from a gold spec).
  • ≥ 3 runs per case per model; report the spread.

6 · Decisions needed from you

  1. Block library location: create fluentvibe/blocks/, or extend workspace_modules.py in place (no new folder)?
  2. Checkpoint: mandatory spec approval in the web UI, or skippable ("trust extraction")?
  3. Off-deck default when the profile has no ODTC: user_prompt with a plate hand-off (recommended), or refuse and ask?
  4. Liquid classes: auto-assign from the catalog map (recommended), or keep them as declared variables for you to fill in?
  5. Decompiled corpus: which FluentControl methods may be used, and may they be committed after de-branding or only kept local?
